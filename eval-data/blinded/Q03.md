QUESTION:
Our Postgres queries are getting slow — some taking 3-4 seconds — but I'm not sure if the bottleneck is missing indexes, query structure, or just the fact that we're doing too many joins. How do I even start diagnosing this properly?

---RESPONSE X--- (see raw/Q03/arm_b.md after unsealing)

## Answer

Start with `EXPLAIN (ANALYZE, BUFFERS) <your query>` — not just EXPLAIN, add both flags. This tells you two things no other tool gives you in one shot: the actual row counts vs planner estimates (divergence here = stale statistics, fix with `ANALYZE <table>`), and the buffer hit/read ratio (shared read >> shared hit = I/O bound, not CPU bound). Look specifically for:

- **Seq Scan on a table with >10k rows** — almost always a missing index. The fix is obvious.
- **Nested Loop with `loops=N` where N is large** — a join is iterating an inner table many times. Fix: check if the inner table has an index on the join column.
- **`rows=10 (actual rows=50000)`** — planner estimate is wildly off. Run `ANALYZE` on that table, then re-run EXPLAIN. The planner will pick a better plan without touching the query.

Second step, run this against `pg_stat_statements`:
```sql
SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 10;
```
This shows you where total wall-clock time actually goes across all executions — not just the one query you're staring at. Optimize the top of this list, not the query that happened to be slow when someone was watching.

Third, check if the slow query is slow *in psql directly* or only through your app/ORM. If it's fast in psql, the problem is connection pooling overhead or ORM generating a different query than you think — not Postgres internals. Add `pg_stat_activity` to check for lock waits:
```sql
SELECT pid, wait_event_type, wait_event, query
FROM pg_stat_activity WHERE wait_event IS NOT NULL;
```

The likely culprits in rough order of frequency: (1) missing index causing Seq Scan, (2) stale statistics causing wrong join order, (3) function applied to indexed column (`WHERE lower(email) = $1` can't use a plain index — needs a functional index), (4) covering index missing (index finds rows but heap fetch is still slow — add the selected columns to the index). "Too many joins" is rarely the root cause — Postgres handles joins fine when cardinality estimates are accurate.

## Dissent worth keeping

The Devil's Advocate position deserves weight before you touch a single index: if you have no connection pooler (PgBouncer or equivalent) in front of Postgres, your 3-4 seconds may be connection establishment overhead that indexing will not touch. Check that first — it takes 10 minutes and can eliminate the problem entirely. More broadly: if the joins are the problem at the data model level (8-table joins to generate a dashboard), query optimization is bounded and the real fix is a materialized view or application-side cache. Every index you add also makes writes slower. Don't assume the bottleneck is inside Postgres until you've confirmed it.

## Confidence

High — EXPLAIN (ANALYZE, BUFFERS) + pg_stat_statements is the deterministic triage path that will isolate the bottleneck class in under 30 minutes for any query in this latency range; the only uncertainty is whether the root cause sits outside Postgres (connection pooling, lock contention), which the dissent covers.

## Answer

Don't guess — measure. Start with `EXPLAIN (ANALYZE, BUFFERS) <your slowest query>` (both flags matter: ANALYZE gives actual rows vs estimates, BUFFERS shows disk vs cache). In parallel, enable `pg_stat_statements` if not already on and query it sorted by `total_exec_time` to find the worst offenders across all executions, not just the one you're staring at. That's your triage in under 30 minutes.

What the EXPLAIN output tells you, in order of how often it's the answer:

1. **Seq Scan on a table with >10k rows** → missing index. Most common. Add the index on the filter or join column.
2. **`rows=10 (actual rows=50000)`** → stale statistics. Run `ANALYZE <table>` to refresh `pg_statistic`; the planner will pick a better plan with no schema change.
3. **High `Buffers: shared read` vs `shared hit`** → I/O bound, working set doesn't fit in `shared_buffers` cache. Either grow shared_buffers or reduce the working set.
4. **Nested Loop with `loops=N` on large N** → join is iterating an inner table many times; check for missing index on the join column or a function applied to an indexed column (e.g., `WHERE lower(email)=$1` won't use a plain index on `email`).

"Too many joins" is rarely the root cause — Postgres handles joins fine when cardinality estimates are accurate. If you see correct plans with correct estimates and still 3-4 seconds, you're in the harder cases: dead-tuple bloat from neglected vacuum (`SELECT relname, n_dead_tup FROM pg_stat_user_tables`), N+1 patterns from your ORM (visible as many short queries in `pg_stat_activity`, not one long one), or lock contention (`SELECT pid, wait_event_type FROM pg_stat_activity WHERE wait_event IS NOT NULL`).

Before adding any index: verify the slow query is slow *in psql directly*. If it's fast in psql and slow through the app, the problem is ORM query generation, connection pool exhaustion, or network — none of which indexing fixes.

## Dissent worth keeping

Devil's Advocate position, preserved: the most common diagnostic trap is jumping to EXPLAIN ANALYZE and adding an index that drops latency to 800ms today, while the real underlying problem — dead-tuple bloat, autovacuum starvation, connection pool saturation — silently compounds, and three weeks later queries are back to 6 seconds. The 5-minute-cheap check before any query tuning: `pg_stat_user_tables.n_dead_tup` vs `n_live_tup` ratios, `pg_stat_activity` lock-waits, and whether a connection pooler exists at all. If you don't have a connection pooler and your app opens a connection per request, that overhead alone can be 2-3 seconds before Postgres even sees the query — and no index will fix that.

## Confidence

High on the diagnostic path (EXPLAIN+pg_stat_statements is universally applicable); medium on the specific fix because without seeing the schema and query text, any concrete recommendation is conditional on what the EXPLAIN reveals.

---RESPONSE Z--- (see raw/Q03/arm_a.md after unsealing)

Start with EXPLAIN ANALYZE. Run it on your slowest queries and look at the actual row estimates vs. actual rows — when the planner thinks a step will return 10 rows but gets 50,000, that's usually where things go wrong. The key numbers to focus on are actual time on each node, and whether you're seeing Seq Scan on large tables (almost always bad) vs. Index Scan.

From there, the diagnosis usually branches into a few distinct causes:

Bad estimates and stale statistics are more common than people expect. If EXPLAIN ANALYZE shows the planner making wildly wrong row count guesses, run ANALYZE on the relevant tables, and check your autovacuum settings — if it's not running frequently enough, statistics get stale and the planner makes poor choices. You can also run pg_stat_user_tables to see when tables were last analyzed.

Missing indexes are easy to spot: look for Seq Scan nodes on large tables combined with a Filter line showing many rows being removed. The fix is usually straightforward — create an index on the filtered or joined column. But pay attention to join order in the EXPLAIN output too; if you're joining a big table to a small one in the wrong direction, an index on the wrong side won't help much.

Query structure issues show up as nested loop joins with huge loop counts, or hash joins that spill to disk (you'll see "Batches: N" where N > 1 in the hash join node). Too many joins isn't inherently the problem — it's usually that the joins are happening in suboptimal order, or that intermediate result sets are exploding in size before the filtering happens. Moving WHERE clauses earlier, using CTEs carefully (in Postgres 12+ they're inlined by default, but in older versions they act as optimization fences), and avoiding SELECT * so you're not hauling unnecessary columns through joins all help here.

For systematic diagnosis, enable pg_stat_statements if it's not already on. It aggregates query stats over time and lets you rank queries by total time, mean time, and call count — which tells you whether you have one catastrophically slow query or many moderately slow ones adding up. That distinction matters because the fix is different.

The practical workflow: pg_stat_statements to find your worst offenders by total_time, EXPLAIN (ANALYZE, BUFFERS) on each one to see the actual execution plan and buffer hits/misses, then check whether you're hitting shared buffers or going to disk (Buffers: shared hit vs. read). If you're seeing a lot of disk reads on a query that should be hot, your shared_buffers or work_mem might be undersized for the workload, which is a configuration problem rather than a query problem.

Don't tune indexes in isolation — each index adds write overhead, so identify the highest-impact ones first rather than indexing everything that appears in a WHERE clause.
