## Recommendation

Don't choose between "stay monolith" and "go microservices" — that's a false binary, and not quite the right axis either. The actual middle ground is: keep one deployable artifact, but stop treating "the code" and "the release process" as the same problem. Decouple how you release — so shipping one team's work doesn't require the whole company's attention — first, because that fix is cheap, reversible, and helps no matter what's really wrong. Then, only if a short audit shows the pain is genuinely about tangled code and shared data ownership rather than the release process, enforce hard module boundaries inside the monolith — not across a network. Extracting an actual separate service should be the last resort, reserved for the rare piece of the system that provably needs its own scaling or failure isolation, not the default move for an 8-person team.

## Why

A monolith becomes hard to deploy "without coordination" for one of two reasons, and they have different fixes. Either the code and data are genuinely entangled — Team A's change breaks Team B's feature because they touch the same tables or the same modules — or the release *process* is entangled: batched releases, one shared staging environment, manual sign-off, slow or flaky CI, migrations that aren't backward-compatible. The second cause is far more common at this scale, and it is fixable with zero architecture change: a merge queue or continuous small-batch deploys, feature flags to separate "shipped" from "turned on," migrations that work with both old and new code during rollout, and a rollback that's a single action instead of an incident. None of that requires knowing whether you'll eventually split anything out.

Full microservices, taken as the first move, has a structural problem at this headcount. On-call capacity doesn't multiply just because the codebase gets split into more pieces: eight people isn't a lot of engineers to begin with, so spreading them across several independently owned services either fragments the rotation below a workable size, or the services end up not really independently owned — which defeats the point. It also only pays off if the services are actually independent: if they still read and write the same database, you've swapped code coupling for network calls and versioning while keeping the coordination cost, which is strictly worse, not a compromise. And unlike a module boundary (a lint rule you can tighten or loosen), a service boundary is expensive to undo once client contracts and deploy pipelines exist around it.

A modular monolith — one deploy, enforced module ownership, no reach-through into another module's tables — gets most of what "microservices" is actually being asked to provide (clear ownership, parallel work without stepping on each other) without paying for a distributed system you don't need yet. But it's real work, not a free lunch: boundaries drawn without CI enforcement tend to erode back into the same tangle within a few months, and boundaries drawn along today's team structure can lock in a team split that might itself be part of the problem.

## What to do

1. **This week (1-2 days, one engineer):** Look at the last ~15-20 deploys that needed coordination or got delayed, and tag each by actual cause — shared staging, manual sign-off, flaky/slow CI, a migration that broke running code, or a genuine code/data conflict between teams' areas. This single audit is what the rest of the plan branches on, so don't skip it.
2. **Next 2-6 engineer-weeks, regardless of what the audit shows:** Fix the release process. Move to a merge queue or scheduled small-batch deploys instead of batched releases. Put unfinished work behind feature flags so "deployed" and "live" are separate. Make migrations expand/contract (old and new code both work during rollout) instead of breaking in place. Get rollback down to one action. Alongside this, get a read on CI health (how long it takes, how often it's flaky) and current batch size (pull requests per deploy) — both usually explain more of the pain than anyone expects, and both are cheap to measure. This step is worth doing under every outcome of the audit.
3. **Only if the audit shows real, recurring code/data conflicts between teams (not process friction):** Draw 2-4 module boundaries along where the conflicts actually are (not the org chart), give each module one owning team and its own tables, add a CODEOWNERS file, and enforce the boundary in CI with a linter for your stack (e.g., Packwerk-style for Rails, ArchUnit/Modulith for Java, import-linter for Python, dependency-cruiser for TS, internal packages for Go). Also count how many tables are written by more than one team's code — that number is the real price tag of any future split. This is weeks of work, not months, and it stays inside one deployable.
4. **Only much later, and only with evidence:** If one specific module has genuinely different scaling or reliability needs from the rest, first try getting runtime independence without a network boundary — run the same build as a separate process (e.g., a web process and a background-worker process from the same codebase). Extract that module as its own service only if it still needs it after that, only once it already has clean boundaries and owns its own data, and only once the basics (fast environment provisioning, basic monitoring, fast deploys) are solid for the one deployable you already have. Budget low-single-digit engineer-months plus a permanent tax in pipelines, on-call, and API versioning — this is not something to do speculatively for parts of the system that haven't proven they need it.

Before committing past step 2, also check: how the 8 people currently split into sub-teams, and whether that split follows real seams in the system or is itself manufacturing cross-team changes; the hiring plan for the next 12-18 months, since headcount growth changes this calculus; and whether anything external (app-store review cycles, an on-prem customer, a compliance sign-off) caps how fast you can ship regardless of architecture — no amount of restructuring fixes a mandatory human sign-off gate.

## Risks of this plan

- The audit gets skipped or rushed under delivery pressure, and the team defaults to "draw some module boundaries" without knowing if that's the actual fix — busywork that doesn't touch the real bottleneck.
- Module boundaries drawn but not enforced in CI tend to erode back to the original tangle within a few months, so the refactor cost is paid without the isolation benefit.
- Boundaries drawn along the current team split can ossify a team structure that's itself generating cross-team changes, making the next reorg harder, not easier.
- Going straight to service extraction instead — the pressure this plan is designed to resist — risks a "distributed monolith" (split code, shared database) that keeps the coordination cost and adds network and versioning failure modes on top, plus an on-call rotation too thin to staff per service.
- Doing nothing while this gets debated has a cost too: batch sizes and blast radius keep growing, deploys keep getting riskier, and the case for "just go microservices" gets louder by default, not because it was tested against the cheaper alternative.

The plan above is cheap to be wrong about: steps 1-2 (the audit and the release-process fixes) are useful no matter what the real cause turns out to be, and step 3 is a lint rule and an ownership file inside the existing codebase — reversible in days if it turns out not to be the bottleneck. The expensive mistake is the reverse order: extracting services first, then discovering the pain was the release process all along, and now owning several pipelines that have to be consolidated back.

## Strongest counter-position

The case for skipping the architecture work entirely, not just deferring it: if the coordination pain is coming from the release process, then modular-monolith work fixes nothing — you'd still be waiting on the same build, the same pipeline, and the same sign-offs after months of boundary work, just with tidier module folders. On this view, the honest move is to freeze *any* architecture change for a quarter and put all the effort into making releases automatic — deploy on every merge through a queue, feature flags, compatible migrations, one-click rollback — because that's the one intervention that helps regardless of how the code is organized, and it needs no decision about module or service boundaries first. Worse, drawing module boundaries right now means drawing them along today's team split, and part of what's producing the coordination pain may be that very split — so the boundary work can quietly lock in the thing that should change instead. It's also worth noticing which option gets proposed by default: freezing architecture and fixing release plumbing is unglamorous and hands no one a signature project, while boundary-drawing work is visible and safe to champion — which is a reason to be suspicious of how quickly "let's do modular-monolith work" becomes the consensus pick. This position wins if the week-one audit shows coordination events are overwhelmingly about batching, staging, sign-off, and migrations rather than teams actually stepping on each other's code — in which case step 3 above should be dropped, not just deferred, and the freeze should hold until the team-structure question is revisited on its own terms.

## Confidence

High: full microservices as the first move is a poor fit for an 8-person team, and release-process fixes (smaller batches, feature flags, safe migrations, fast rollback) are worth doing regardless of the eventual architecture — nothing about this depends on facts specific to this team.

Medium: whether module-boundary enforcement is the second step that's actually needed. This is the one load-bearing unknown — every path above rests on not yet knowing whether the coordination pain is code/data coupling or release-process friction, which is exactly what the week-one audit is for. Treat any recommendation that skips straight to "enforce these boundaries" (including this one, past step 2) as provisional until that audit runs.

Material unknowns: the actual cause breakdown behind recent coordination events (the audit answers this); whether the current sub-team split tracks real system boundaries or is itself manufacturing cross-team changes; whether the team is about to grow enough to change this calculus; and whether any external constraint (compliance, app-store review, a major on-prem customer) caps deploy frequency independent of architecture.
